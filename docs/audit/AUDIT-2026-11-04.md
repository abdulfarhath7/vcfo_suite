# VCFO Suite audit (2026-11-04, branch as found, read only)

**What this repo does:** VCFO Suite is the compliance cockpit for SBC, an Indian professional-services firm.
It runs company incorporation (questionnaire, 34-step SPICe+ checklist, generated Word documents, board
resolutions), the recurring compliance calendar, board meetings, labour registers and receivables, for staff
(super admin, admin, manager, lead) and clients, on Next.js 16 + Postgres (Drizzle) on AWS App Runner.

**Load assumed:** one firm. Tens of staff, a few hundred client logins, a few hundred engagements. App Runner
with 1 to 2 instances of 1 vCPU / 2 GB (`infra/app.tf:129-131`, `infra/variables.tf:70-75`), one Postgres pool
of 10 connections per instance. Findings are judged against that, not against "web scale".

Severity: Must = bug, security, data loss, breaks at this load. Effort: S < 1 h, M = half a day, L = days.

---

## Must fix

1. **Scheduled jobs probably do not run in production** (`docs/context/STATE.md:71`, `src/jobs/client.ts:8`, `app/api/receivables/sheets/[id]/send-summary/route.ts:21`) — Must, S (ops)
   - **What this is:** Every reminder in the product is an Inngest job (a hosted scheduler that calls `/api/inngest`): compliance reminders, board-meeting T-10 bells, receivables reminders, FX rates, the weekly digest, task repeats.
   - **Problem:** STATE.md still lists "Inngest cloud keys" as not done, and the send-summary route says in its own comment that the keys are not set on App Runner (that is why it uses `after()`). Without `INNGEST_EVENT_KEY` / `INNGEST_SIGNING_KEY` no cron fires. Clients and leads get no reminders, and nobody is told.
   - **Fix:** Put the two keys in Secrets Manager and on the App Runner service (Terraform), sync the app in the Inngest dashboard, then check `/app/dev/jobs` shows runs. If the keys are in fact set, update STATE.md and the route comment.
   - **If we skip it:** Statutory deadlines pass without the reminders the firm sells.

2. **Sign-in has no rate limit, and `/api/auth/two-step` is a password oracle** (`app/api/auth/two-step/route.ts:20-24`, `src/auth/config.ts:73-74`, `src/lib/growth/demo-request.ts:86-89`) — Must, S
   - **What this is:** The login form first posts email + password to `/api/auth/two-step` to learn whether to ask for a code, then calls Auth.js `authorize`.
   - **Problem:** Neither path is throttled. For any account with two-step on, `codeRequired: true` comes back only for the right password, so an attacker can guess passwords without ever touching the TOTP lockout. Each guess also runs a bcrypt compare (about 100 ms of CPU), so a few requests per second pin the single vCPU for every user. The existing `clientIp` takes the *first* `X-Forwarded-For` entry, which the caller writes; App Runner appends the real address at the end, so the demo-request and meeting-reply limiters can be bypassed too.
   - **Fix:** Reuse `createRateLimiter` from `src/lib/growth/demo-request.ts` (keyed by IP and by email) in both the two-step route and `authorize`. Change `clientIp` (and the copy in `src/auth/config.ts:36-39`) to take the last `X-Forwarded-For` entry.
   - **If we skip it:** Password guessing on staff accounts, and an easy way to make the app unusable.

3. **Confirming a bank credit can pay two sets of invoices, and partial failures leave the books half-updated** (`src/db/repositories/receivables/credits.ts:29-56`, `src/db/schema-receivables.ts:242`) — Must, S
   - **What this is:** A bank credit is matched to one or more open invoices; `confirmCredit` marks them received.
   - **Problem:** It reads the credit status, then marks invoices, then flips the credit, with no transaction and no conditional update. Two managers (or a double click) confirming the same credit on different invoices both pass the status check, so one ₹ credit marks two invoices received. If `logChange` throws halfway, some invoices are received while the credit still says "to confirm". Separately, the code says a credit counts "once per sheet whatever the source", but the unique index is `(sheet_id, source, external_ref)`: a hand-imported statement and the hourly feed racing on the same credit both insert, and both auto-settle.
   - **Fix:** In `db.transaction`, first `update bank_credits set status='confirmed' where id=? and status in ('to_confirm','unmatched') returning`; stop if no row; then settle with `and status='open'` in each invoice update. Change the unique index to `(sheet_id, external_ref)` (one migration).
   - **If we skip it:** Invoices shown as paid that were not paid; reminders stop for real debts.

4. **Client "Download all" builds the whole ZIP in memory, with no cap, re-resolving scope per file** (`src/db/repositories/client-documents.ts:561-628`) — Must, M
   - **What this is:** The client Documents page lets a client download a folder or everything as one ZIP.
   - **Problem:** Every file is read fully into memory (`getObjectBuffer`), then PizZip builds a second full copy, then the response copies it again. There is no file or byte cap. For each file `resolveClientDocumentFile` re-runs the engagement lookup (one more DB query, sometimes two), sequentially. A client with 300 MB of scans uses about 1 GB of the 2 GB instance; two clients at once can crash the instance for everyone. The staff vault already solved this: `app/api/documents/zip/route.ts` streams with `createZipStream` (`src/lib/zip/zip-writer.ts`) and caps at 500 files / 1 GB.
   - **Fix:** Resolve the engagement once, then hand the picked files to `createZipStream` + `openObjectStream`, with the same caps. Delete the PizZip path. Net code goes down.
   - **If we skip it:** Out-of-memory restarts during a busy filing week.

5. **Legacy client invites: any signed-in user can accept any invite token; expiry ignored; token from `Math.random`** (`src/db/repositories/invites.ts:70-71,86-100`, `app/api/invites/route.ts:42-50`, `src/context/app-provider/use-record-actions.ts:99-132`) — Must, S (delete)
   - **What this is:** The demo-era "invite a client by link" flow. Real client logins now use `client-team` invites with hashed one-use tokens.
   - **Problem:** `acceptInviteByToken` ignores its `ctx` and `expiresAt`: any lead, manager or client who has a token string can mark it accepted and read back its email and engagement. The token is made in the browser with `Math.random` (guessable) and the server trusts a caller-supplied token. `inviteClient` is not called by any view; `/invite/[token]` only works with demo auth on.
   - **Fix:** Delete `invites.ts` (+ test), `app/api/invites/route.ts`, `app/invite/[token]/page.tsx`, `src/views/auth/InviteAccept.tsx`, the `inviteClient` / `acceptInvite` / `invites` members of the app context, and the `/api/invites` query in `use-server-sync.ts:115` (one fewer request per page load). Keep the table until a later migration drops it.
   - **If we skip it:** A dead path with a live hole that the next feature may wire back up.

6. **"Due soon" means four different things, and the staff side uses the UTC day** (`src/lib/client-portal/compliances.ts:24`, `src/lib/compliance/filings.ts:140,151`, `src/components/client-portal/pages/home/derive.ts:252`, `src/components/admin/statutory-calendar-utils.ts:232`) — Must, S
   - **What this is:** Every compliance list colours a filing Overdue / Due soon / Upcoming.
   - **Problem:** The window is 7 days on the client calendar, 14 on staff filings, 15 on the client home and the obligations rail, 7 on the admin statutory calendar. A filing due in 10 days is "Due soon" on the client home and to staff, but "Upcoming" on the client's own calendar. Also `filingStatus` takes "today" as the UTC date, while the client side uses IST: from 00:00 to 05:30 IST a filing due yesterday reads as due today for staff, not overdue.
   - **Fix:** One exported `DUE_SOON_DAYS` (owner picks the number) in `src/lib/compliance/filings.ts`, imported by the other three, and compute today with the existing IST helper (`todayIST`). This is a bug fix, so touching ported compliance code is allowed by rule 3. Add one test that the client and staff status agree for the same row.
   - **If we skip it:** The client and the firm disagree on what is urgent, in a product sold on deadlines.

## Should fix

7. **A route imports `db` directly, and the auth layer does too** (`app/api/engagements/[id]/route.ts:36-38,83-96`, `src/auth/guards.ts:4-5,73-88`, `src/auth/config.ts:5-6`) — Should, S
   - **What this is:** Golden rule 1: only `src/db/repositories/*` may import `db`.
   - **Problem:** The engagement PATCH route has its own `profileParty` query on `profiles`. Guards and Auth.js config also query `profiles` directly. These are the only three files outside repositories that do.
   - **Fix:** Move `profileParty` into `profiles.ts` as a `system*` reader (one exists for most needs already) and the `currentContext` row read into `profiles.ts` / `user-sessions.ts` next to `systemIsSessionActive`.
   - **If we skip it:** The seam erodes "for just one query", which the rules forbid.

8. **Slow work runs inside the request in many routes** (`app/api/board-meetings/[id]/approve/route.ts:9-21`, `app/api/engagements/[id]/doc-pack/zip/route.ts:13-22`, `src/lib/api/doc-pack.ts:160-181`, 23 routes awaiting `notifyEngagementEvent` / `notifyTeamAssignment`, e.g. `app/api/engagements/[id]/route.ts:195,220`) — Should, M
   - **What this is:** CLAUDE.md says docx, ZIP and outbound email belong in a job.
   - **Problem:** Approving a board meeting renders the Word notice, the `.ics`, creates a Teams meeting through Graph and emails every director before the response. The doc-pack ZIP renders every docx one after another. Checklist submit/review and team changes wait on the email provider. One slow Graph or SES call holds the user's click for seconds, and a provider timeout returns an error after the data was already saved.
   - **Fix:** Until finding 1 is done, use the pattern already in `send-summary/route.ts`: save, record "sending", return, and do the send in `after()`; return the email outcome by polling or the bell. Once Inngest runs, move these into jobs.
   - **If we skip it:** Spinners of several seconds and "failed" toasts for work that succeeded.

9. **Client and staff compliance pages are two parallel apps** (`src/components/client-portal/pages/compliances/` 7,331 lines vs `src/views/compliances/` 10,554 lines) — Should, L
   - **What this is:** The "one page per feature" rule: a feature has one page for every role.
   - **Problem:** Status words, due-soon rules (finding 6), obligation grouping (`client-portal/pages/compliances/obligations.ts` vs `views/compliances/obligation-groups.ts`), calendars and month navs (`MonthNav.tsx` vs `month-nav.tsx`) are written twice and already disagree. Documents has the same split, smaller (`client-portal/pages/documents/` 4,706 lines vs `views/vault/` 2,163), though staff already reuse the client explorer through `StaffClientDocuments.tsx`.
   - **Fix:** Start with the pure helpers: make the client pages use `src/lib/compliance/filings.ts` status and `obligation-groups.ts`, then merge the calendar and month nav. Leave the shells different; share the logic.
   - **If we skip it:** Every rule change needs two edits, and finding 6 happens again.

10. **Super admin keeps a second, legacy client incorporation UI** (`src/components/client-portal/pages/incorporation/index.tsx:20-22,64`, `src/views/client/Incorporation.tsx`, `src/views/client/BoardResolutionView.tsx`) — Should, M
    - **What this is:** When a super admin opens a client page inside the staff shell, the old client views load instead of the v7 portal pages.
    - **Problem:** About 500 lines of client UI exist only for that preview and must track the real client pages.
    - **Fix:** Render the portal pages (`IncorporationLanding`, `BoardPage`) inside a `.cp` wrapper for the super admin too, then delete the two legacy views.
    - **If we skip it:** The super admin previews something the client no longer sees.

11. **Dead page: `src/views/client/Overview.tsx`** (159 lines, plus `Overview.test.tsx`, 237 lines) — Should, S
    - **What this is:** The pre-v7 client overview.
    - **Problem:** Nothing imports it except its own test (grepped `src`, `app`, `e2e`); `/app/client/overview` renders `HomePage`.
    - **Fix:** Delete both files.
    - **If we skip it:** 396 lines that run in CI and mislead readers.

12. **Hand-written role checks that should use the helpers** (`src/db/repositories/profiles.ts:68,114,191,418,741,804,844,880`, `src/db/repositories/client-change-requests.ts:288`, `src/db/repositories/audit-events.ts:99-105`) — Should, S
    - **What this is:** CLAUDE.md requires `isAdminOrManager` / `isFirmWideAdmin`; hand checks dropped `super_admin` seven times before.
    - **Problem:** These eleven are correct today (they list `super_admin`), but they are the same three-role list typed out by hand; the next role change (`developer`, `partner` were both added this month) has to find all of them.
    - **Fix:** Replace each `ctx.role !== 'admin' && ctx.role !== 'super_admin' && ctx.role !== 'manager'` with `!isAdminOrManager(ctx.role)`.
    - **If we skip it:** The next role added is let in or locked out in a few of these places.

13. **Money code without a repository test: bank-credit settle and ingest** (`src/db/repositories/receivables/credits.ts`) — Should, S
    - **What this is:** The code that marks invoices received from bank credits (finding 3).
    - **Problem:** `match.ts` and `camt.ts` are tested; the repository that writes the result is not. A double confirm or a duplicate import would not fail any test.
    - **Fix:** One test: ingest the same credit twice from two sources, then confirm it twice; expect one credit row and each invoice received once.
    - **If we skip it:** Finding 3 comes back unnoticed after any refactor.

## Nice to have

**Verdict:** Fix 1 (turn the scheduler on), 2 (throttle sign-in) and 3 (bank-credit race) first; 4 and 5 are each under a day and remove code.

**Lean:** about -1,500 lines possible (invites flow ~300, client Overview 396, legacy client incorporation views ~500, PizZip client ZIP ~70, plus merged compliance helpers), -0 dependencies (`pizzip` stays for docx).

**Not checked:** Ported domain code (`src/lib/checklist`, `src/lib/board-resolution`, `src/lib/incorporation-docs`, `src/data/checklist.ts`) except where it feeds finding 6; Ask VCFO pipeline and evals; labour-register parsing and renderers; the developer console (`/api/dev/*`, only `devAction` guarding checked); Terraform beyond sizing; Playwright specs. Nothing was run (no typecheck, tests, build or bundle analysis); App Runner environment variables were not inspected, so finding 1 rests on STATE.md and the code comment.
