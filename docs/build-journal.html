The decision everything else hangs from05

Rent someone else's box, or own the whole thing.

The original app was built on a rented service that bundled the database, the login and the file storage together. Convenient to start, but it decides your pricing, your limits and where your clients' documents sit. On 7 August that bundle was taken apart and each piece replaced with something the firm controls.

Before · one rented bundle

Database theirs, priced their way
Login & passwords theirs
Client documents on their storage
Security rules written in their language, hard to test
One supplier holds the data, the identity and the bill. Moving later would be a rewrite.
→

After · four replaceable parts

PostgreSQL the standard business database — runs on a laptop, a server, or Amazon, unchanged
S3-style file storage documents; local copy in the office today, Amazon later, same code
Auth.js login and sessions, owned in our own code
One access gate every request checks who you are before touching data
Any one part can be swapped without touching the rest. That is the whole point.
What it bought
Choice of where data lives
Office machine now, Indian cloud region later. A configuration change, not a rebuild.
No day-one cloud bill
The same code runs on office WiFi. Pilot first, pay later.
Rules we can test
Access rules now live in ordinary code, so automated tests can prove them.
One place to look
All data access funnels through 23 gates. Audit means reading 23 files, not the whole app.
What it cost
Two days of rebuild before any new feature
Login broke and had to be repaired
Database setup broke and had to be repaired
Every screen had to be re-pointed at the new data path

A real vulnerability, found and closed.

The problem

User information was being kept in the browser itself. That means it sat on the individual laptop, survived after logout, could be read by anyone with that machine, and was lost the moment someone cleared their browser or switched devices.

Act 2 · build the product09
09Aug

The cost problem nobody sees until the bill arrives.

Files are the product's main cargo. Files are also what a cloud charges for.

This app moves documents constantly — identity papers, incorporation forms, signed resolutions, bank letters. On a cloud, you pay to store them and you pay again every time someone opens one. So the day went to a single question: can we make each file smaller, once, without ever making it harder to read or less safe?

Researched file-shrinking methodsWhich ones keep the document perfectly readable
Found approaches that shrink and protect togetherSmall enough to be cheap, scrambled enough to be safe at rest
Blocker: shrinking makes uploads feel slowThe user waits while the machine works
Blocker: when to shrink — and what to never touchIdentity documents must stay untouched originals
Answer chosen: once, at first upload, never againThe user pays the wait one time; the firm saves every month after
Day spent on design, not codeDeliberately — the wrong answer here is expensive to undo
Status: designed and decided, not yet switched on. It becomes worth building the day the app moves to a cloud bill — which is exactly why it was designed before that day, not after.

Meeting outcome · India's data protection law (DPDP)

Seven obligations that now sit on the product roadmap. This is the list the firm will be measured against.

1 · Know your data
A written inventory of every piece of personal information: what, why, where, who can reach it.
2 · Ask permission
Privacy notice, consent, and screens where a person can exercise their rights.
3 · Do not keep it forever
Automatic retention limits and real deletion.
4 · Lock it down
Strong access control on anything personal.
5 · Watch your suppliers
Track every outside service that receives user data.
6 · Plan for the bad day
A breach process and a grievance channel, defined before you need them.
7 · Check yourself
Regular audits, not a one-time certificate.
Where this stands
Points 4 and 7 are largely built. See the DPDP scorecard later in this book.

Managers can act. Admins stay in control.

Part one of two: project administration — the biggest governance change in the build.

Until today, a project could not be edited after creation, could not be deleted, and carried one manager and one lead. Today it became a properly governed record — with a rule about who may do what, and a paper trail for the rest.

A manager may do directly

Edit project details Update entity information Adjust the delivery team Update the questionnaire
Low-risk. Reversible. No approval needed.
→

A manager must request

Delete a project Change the client Reassign the manager
The request carries the exact proposed change. The admin approves that exact change — the decision can never differ from what was reviewed. If it fails to apply, the request re-opens instead of falsely reporting success.
Delete is a recycle bin, not a shredderA deleted project disappears from every screen at once, but its documents, checklist history and audit trail survive intact — and a firm admin can restore it
Approvals queue for pending requestsVisible to both the requesting manager and the deciding admin
Actions menu on every project cardEdit, change client, delete. Options a manager can only request are shown and labelled, not hidden — so the path stays obvious
Two admins deciding at once produce one winnerNo double-execution, no contradictory outcome
Several managers and several leads per projectAssigned at creation. A manager creating a project always includes themselves
Compliance questionnaire at intakeSeven lettered sections from the firm's own questionnaire, with its real conditional logic — answer No and the follow-up questions disappear, and any stale answers behind them are cleared so they never reach the record

1 · Data inventory
What we hold, why, where, who reads it

Tell people, ask people, let them act

Not started

Do not keep it forever
Projects now delete into a restorable recycle bin, which is the foundation. Automatic time-based expiry and true permanent erasure are still to come.
Foundation laid

Plan for the bad day

Not started

Check yourself, regularly

Largely done
